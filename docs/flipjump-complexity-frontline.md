# Complexity front line: stl-additions / stl-seq-ptr (rev 2, 2026-10-24)

Rows = EXISTING stl macros whose own cost changed on these branches (or whose documented line was already wrong). Their lines stay unchanged in the repo: the "proposed" column is for the owner. The NEW macros' lines are committed (stl-additions fcdba7f, stl-seq-ptr 321daa3, both pushed) and listed in section 7. Macros that change only through a call (add_constant, ptr_inc, mul10, div / idiv, the pointer *_and_inc ops, ...) are not rows.

## 1. The conventions, reconstructed from the classic docs

- **C1, @** = log2 of the program's ops. A code address in such a program has about @/2 on-bits.
- **C2, a wflip costs the on-bits of the VALUE it flips**, in time and in space (one in-stream op plus popcount-1 chain ops). A general address: @/2. A `pad 2^k` label: @/2 - k/2 (pad 16: @/2-2, pad 4: @/2-1).
- **C3, the classic docs compose documented costs**: hex.xor = @ / @+12 (two pad-16 wflips @-4, plus 3 executed ops; 16 table entries in space: @-4+16 = @+12); xor_zero = @+4 / @+28 (the count is @+1 / @+27: @-4 plus 5 executed ops, 31 entries; the doc rounds up, and @+4 / @+30 is measured); zero = xor; if = @-1 / @+15; jump_to_table_entry = xor + xor + @/2 + @/2 + xor_zero = 4@+4 / 4@+52. Every front-line line below reconstructs exactly this way (section 6, column "old derivation").
- **C4, the shared tables are not charged to a call**; their executed ops are (or/and 6, add/sub 8, the add_mul flow @+24).
- **C5, n-hex lines keep only the n terms** in the classic docs too: add n drops its two clear_carry brackets, read_hex n its final ptr_sub.
- **C6, space is counted without the assembler's tail sharing** in the classic docs. The assembler shares a chain tail between wflips with the same RETURN address and the same remaining bits, so a wflip whose return is shared (xor_zero's set on .res, the .ret set returning to a table's jumper, if_flags' set on one hex) emits only its low bits. Measured: in classic or n, 2 of the 8 wflips a hex emit 2.5 and 3.4 instead of 8.2 and 9.2: that is why eacc7ee measures n(3@+63), not the doc's n(4@+52). The proposed space lines count this sharing where the chain's structure guarantees it (each step's xor_zero shares the previous step's tail: 2.5@+58 a hex).
- **C7, wflips whose value is a stl init label** (hex.pointers.to_flip / ret_after_read_byte, the mul table's after_add) flip a LOW address: their popcount is a constant (to_flip: 3, measured), not @/2. The classic docs count them as @/2 (read_byte_from_inners_ptrs 5@+13, the flow @+24); the proposed lines keep that convention so old and new compare, and the "verified" column says where it makes the measured @ coefficient lower.

Measured check of C2 (the wflip ledger, below): every pad-16 wflip's popcount rises by exactly 0.5 per @ between the two placements (hex.xor: 7.75 -> 8.75 for @ 18.42 -> 20.42); general addresses sit at @/2 (9.15 at @ = 18.45). At these two placements a pad-16 value has 0.5-1 more on-bit than @/2-2 (8.1 at @ = 18.45), so the measured constants run 0.5-1 per pad-16 wflip above the derived ones; the @ coefficients are unaffected.

## 3. The README

Added (stl-additions fcdba7f), under the bullet that explains @, in that section's style:

> - A chained step's wflip (`wflip .ret+w, prev_return ^ return`, see `hex.tables.chained_jump`) flips the xor of two nearby pad-16 return addresses, so it costs 2.3 on average (median 2, 90% at most 4; measured over the hexlib tests' 47,598 steps), not @/2.

PROPOSED (not applied) for the bullet itself, which names the wrong operand: `wflip address, value` costs the on-bits of the flipped VALUE, not of the address it writes to:

> - The reason for this _weird_ log complexity, is that `wflip address, value` has the complexity of the number of on-bits in _value_ (usually an address, so about @/2); And it is widely used.

(the diff: "_address_" -> "_value_ (usually an address, so about @/2)".)

## 4. The method

- time = executed ops, space = EMITTED ops (every `insert_fj_op` and wflip-chain spot the assembler creates, wherever it lands), each as (K = 4 calls - no calls) / 4 in one program; `scratchpad/stlx/measure_emit_heavy.py`. The calls sit at op 349,525 or 1,398,101 (half-ones addresses): @ = 18.4 and 20.4. It reproduces the classic docs: hex.xor @ / @+13 (doc @ / @+12), xor_zero @+4 / @+30 (doc @+4 / @+28).
- The wflip ledger (`wledger.py calls`, results `wl_*.json`): every wflip a call emits, by source line, with its value's popcount and the ops it emitted. It reproduces measure_emit_heavy's numbers (xor 18.2 / 31.5).
- Fits (`fit3.py`): n^2 / n / constant terms each a@+b at both @; a constant is shown only when >= 10% at n = 16 (the slope is the full fit's, not refitted).
- The proposed lines are DERIVED (C1-C7); the measured values check them (formula / measured at the largest n).
- w=32: the hex arithmetic is width-independent (14 of 14 values equal); the pointer rows are measured at both.

## 5. Where the measured @ coefficient differs from the derivation, and why

1. **Space, tail sharing (C6)**: the classic lines over-count space by about @/2 per wflip whose return is shared; the proposed chain lines include it (2.5@ a hex, measured 2.5@).
2. **Time, init-label wflips (C7)**: add_mul n measures 3@+44 a hex, not 4@+30 (the flow's after_add); read_back 7@+8, not 9@+13 (four to_flip / ret_after_read_byte wflips at popcount 3). The values agree within 4-28%.
3. **Worst case vs average**: hex.mul's `if n` exits early (1.13 at n = 16); fixed_div uses idiv's loop, not idiv's doc (which is 2.3x over at n = 8).
4. **Placement**: a pad-16 value had 0.5-1 more on-bit than @/2-2 at the measured placements (section 1): the measured constants run high by that much per pad-16 wflip.
