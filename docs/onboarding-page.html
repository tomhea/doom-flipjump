doom-flipjump · a guide to the generated artifact

The program the assembler sees
107,564,059 characters. One frame. No loop.

This is not a tour of the Python that builds DOOM in FlipJump. It is a tour of what that Python emits — the generated program itself: where main is, why there is no main loop inside it, and which macro paints a wall column’s pixels.

01where_is_main:

The assembler is handed nine files in a fixed order: a generated constants file (fj_consts.fj, written out by src/doomfj/config.py), then the seven hand-written library files in src/fj/, which define macros and nothing else. Every executable instruction in the program lives in the ninth — one generated file, produced by emit_wall_renderer() in src/doomfj/wall_renderer.py and cached as scratchpad/fjmcache/b_<hash>.fj.

fj_consts.fj› fixed_point.fj› present.fj› projection.fj› frame_render.fj› plane_render.fj› plane_bands.fj› stream_render.fj› THE EMITTED MAIN

That emitted main is 4,756,278 lines long. Almost all of it is baked data and unrolled per-seg code. The actual top-level program — everything that runs in sequence from startup to halt — is 46 lines, and here it is in full, copied verbatim out of the certified build.

Reading a line: the leading number is a WIDTH

Almost every instruction starts with an integer — hex.mov 8, viewx, vx, hex.zero 1, full, hex.xor_by 8, seg_v1x, 62914560. It is the operand width in hex digits (nibbles), not a value. So 8 means a 32-bit register (eight nibbles, the 16.16 fixed-point size), 2 is one byte, and 1 is a single nibble — which is why the one-nibble latches like full are zeroed with hex.zero 1. Read the width first and the listings parse.

  1. Startup runs before this, and line 2 is the jump that gets here. The file opens with stl.startup_and_init_all (which builds the hex.* and pointer truth-tables), and line 2 is literally ;__hot_end — a jump over the ~300,000 lines of register declarations and baked tables that follow. Data in FlipJump is code that must never execute, so it is always jumped past. The label reads “hot end” because it marks the end of the hot data block, not the end of the program; it is where control lands.
  2. This is the entire input. Three decimal integers read from stdin: vx, vy, viewangle. Nothing else enters the program. A malformed number jumps to bad, which halts.
  3. Per-frame setup. wedge_setup builds the conservative 45° field-of-view wedge used to reject segs without any multiplies; ;e1m1_dsc_walk is the descend-only point-location pre-walk that finds the subsector containing the eye and sets viewz.
  4. The frame opens, the walk runs, the frame closes. begin_frame_collines emits the single byte 0x0B; the BSP walk then streams the whole picture out inline as it visits subsectors front-to-back; 0xFF ends the frame.
  5. stl.loop is a halt, not a loop. It is a jump to itself. The program is over — even though 4.4 million lines of the file still lie ahead of it. Those are never reached by falling through; they are jumped into by stl.fcall or read as data through a pointer.
Reading ;label

Lines 38 and 41 look like nothing, but they are the two that connect this 46-line program to the entire renderer. In FlipJump a bare ;target is an unconditional jump — the whole instruction set is a;b, “flip the bit at a, then jump to b”, and omitting a flips nothing. So ;e1m1_bspcode_walk means “go run the BSP walk”, and it comes back by ending with a jump of its own to bsp_done, the label on the line after the call. (A leaf that must return to many different callers cannot do that, which is what stl.fcall/stl.fret and their per-call return registers are for.) The same syntax with a value in front, ;0x1f * dw, is how a data byte is written — see data_banks.

Seven files, not one

The program used to be emitted as a single 4.76-million-line file, which meant the 46 lines you actually read shared a file with 4.3 million lines of baked sprite art. It is now emitted as seven files, handed to the assembler in this order. Only one of them contains the program, and it is the small one.

Why the order cannot be changed

Top-level labels in FlipJump are global, so N files assembled in this order are exactly equivalent to their concatenation — which is how the split was proven safe: the concatenation is byte-identical to the old single file, and the four-viewpoint gate returns the same op counts to the digit. Sorting these paths, or letting a glob decide the order, would silently relocate every baked address constant in the program.

02where_is_the_main_loop:

There isn’t one. This is the single most surprising thing about the project, so it is worth stating flatly: one run of the binary renders exactly one frame and halts. There is no game loop, no frame counter, no state carried from one frame to the next.

The program is a pure function of its stdin. Give it a position and an angle, get back a picture. The loop lives outside, host-side: scripts/walk_e1m1.py re-runs the binary once per frame with new numbers on stdin, driving it through FjmRunner in src/doomfj/fastrun.py.

The memory image must be restored between runs, and that is not an optimisation detail — it is what makes the inverted structure necessary. FlipJump self-modifies as it executes: every wflip rewrites the program, and this renderer’s entire per-seg constant machinery is built out of self-modification. A second run on a dirty image is not the same program.

Measured, not theorised

Reusing the memory image was tried, and measured: run 2 on a dirty core halts after 9 ops (recorded in the module docstring of src/doomfj/fastrun.py, alongside the timings below). The bulk set_words restore in FjmRunner is load-bearing, and is commented as such so nobody “tidies it away” later.

What the host hoists out of the per-frame path is everything that does not depend on the frame — parsing the .fjm, building the segment list, computing the contiguous word runs. That is the difference between a 2.56 s frame and a 0.187 s one; the actual C run loop is 0.105 s of it either way.

03the_walk:

The BSP tree is not walked by a runtime tree-traversal routine reading node records from memory. The tree is emitted as code: each of E1M1’s 470 nodes becomes its own block, with its partition line baked in as compile-time constants, and each of the 471 subsector leaves becomes a straight-line sequence of calls for the segs it contains. Recursion uses one return register per node — the tree is finite and each node is entered exactly once by its single parent, so no runtime stack is needed.

Here is the root node. Everything the renderer does per frame is visible in this one block.

  1. Occlusion prunes the tree. full is a latch set once every screen column has been painted. Because the walk is strictly front-to-back, a full screen means this entire subtree is invisible — so the node returns immediately. This is exact, not an approximation: the per-seg leaf would have returned on full for every seg anyway.
  2. The side test. SET the partition constants, call the shared point_on_side leaf, CLEAR them, then branch. The near child is visited first, the far child second — which is what makes the subsector order front-to-back.
  3. The stop latches. A seg that only attributes floor/ceiling planes is skipped once attribution can no longer change. The compound test tsbstop | (tsstop & fbspent) is load-bearing: plain tsstop here dropped stair-riser pieces, because pieces still record into columns that are attributed but not yet drawn. (tsstop = surface attribution can no longer change; fbspent = the per-frame step-face budget is full; tsbstop = the counter's overflow fuse. Together they mean “this seg provably cannot write anything”.)
  4. SET → USE → CLEAR, twice per seg. Seg 10 is a one-sided wall. Its geometry constants are installed, pass 1 projects it and claims columns, and if it turns out visible (proceed), its render constants are installed and pass 2 emits pixels. Both constant blocks are then cancelled.

Why SET/CLEAR instead of just assigning

Each seg’s constants live in a shared block that is emitted once and called twice — and the two calls are identical. That works because the block is built from hex.xor_by, and xor is an involution: x ^ v ^ v = x. Calling it once loads the values into zeroed registers; calling it again returns them to zero, ready for the next seg.

Why this is faster than hex.set

hex.set must first zero the register it is about to overwrite, and that zeroing costs an @ dispatch — expensive at this program scale. hex.xor_by has none. The catch is that it is only correct on a zeroed register, which is exactly what the CLEAR call guarantees for the next seg. Getting rid of the CLEAR is a real bug: seg constants accumulate and every seg after the first is wrong.

04data_banks:

Roughly 4.4 million of the file’s 4.75 million lines are data. In FlipJump a data cell is an instruction — one whose bits are read rather than executed — so a lookup table is written as a run of jumps that nothing ever jumps to.

A packed byte is one op, and the byte lives in that op’s data bits. The palette below is the DOOM PLAYPAL, three bytes per entry:

The device never receives these bytes over the wire. It is handed the address of the bank once and DMA-reads it straight out of program memory, which is why a table costs approximately zero fj ops to “send”.

Some tables are not read at all — they are jumped through. A dispatch table is a generated ns whose lookup xors the index directly into a jump address, so the table entry is the control flow:

  1. The index is xored into the jump target .dsp, so the jump lands on the entry for that index. Then wflip rewrites the shared return address to point back here — the program editing itself mid-lookup, which is the normal way to do a computed call in FlipJump.
  2. Line 283,254 undoes the wflip. Every self-modification in this program is paired with its own undo, for the same reason the xor blocks are: the next caller must find the machine in the state it expected.

05the_macro_library:

The seven library files define macros only — not one of them emits a top-level instruction. A macro in FlipJump is compile-time textual expansion, not a function: instantiating one pastes its body in. That is why the heavy per-seg bodies are deliberately kept in one shared stl.fcall leaf rather than inlined at each of the call sites the map's 1,378 segs generate (each seg emits several) — the assembler is roughly cubic in the number of unrolled ops.

That has a practical consequence when you read the generated file. The walk calls seg_pass2_leaf, but no macro has that name — it is a label, and the line beneath it is the single instantiation of the macro that does the work. All the leaves sit together, immediately after the top-level program, and this block is the map from generated label to library macro:

So the chain is: the walk calls seg_pass2_leaf; that label is frame.seg_pass2_leaf_body_lines, defined in src/fj/frame_render.fj. The long numeric argument lists are the build's compile-time configuration — screen geometry, budgets, feature flags — frozen into the program at emit time.

One clarification, because the division of labour matters. Pass 2 is where a column's pixels are decided: it projects the seg, derives the wall's top and bottom row for each column, picks the distance-shaded colours, and clips against what is already drawn. It then calls stream.emit_col_lines in src/fj/stream_render.fj to turn that decided column into device bytes. For the geometry and lighting, read pass 2; for the wire format, read the emitter.

fixed_point.fj

ns hex · 10 macros

The Q16.16 arithmetic kernels, plus the table-reading contracts everything else depends on. No floating point exists anywhere in the project.

fixed_mul_lo
Bit-identical to a full multiply, ~3× cheaper: only the nibbles the result can see are computed.
read_table_packed
Reads an entry from a packed-byte LUT. Called by projection.fj throughout.

present.fj

ns present · the wire protocol

Pure emitters: every macro writes command bytes and touches no state. This file is the authoritative spec for the device protocol.

begin_frame_collines
Emits 0x0B — the shipped frame format. Called once by the main.
set_palette / load_raster_tables
Hand the device a bank address; it DMA-reads the rest.

projection.fj

DOOM’s own math, mirrored bit-for-bit against the Python oracle, which is itself a mirror of r_bsp.c / r_segs.c / r_things.c. id Software’s variable names are kept on purpose.

The hot one: a seg’s two vertices → the screen column span it covers.
project_thing
R_ProjectSprite — a monster or item → its on-screen rectangle.

The shared BSP side test every node block calls.

frame_render.fj

The per-seg leaf bodies the walk calls into. This is where a seg becomes claimed columns and recorded surfaces.

seg_pass1_leaf_body_lines
Pass 1: project the seg, claim the columns it wins, set proceed.
seg_pass2_leaf_body_lines
Pass 2: the macro that paints a wall column’s pixels.

Sprite pre-pass: records visible things into per-column slots.

stream_render.fj

ns stream · 41 macros

Turns a column’s decided surfaces into device bytes. Pass 2 calls into here for every column it paints.

The shipped per-column entry point: ceiling bands, wall runs, floor bands, sprites.

The two-sided whole-frame assembler, plus the ditto compression that lets an identical column cost two bytes.

ns plane · 2 macros

Builds the per-column ceiling/floor band lists — the run-length form of a distance-shaded flat, so the floor costs runs rather than pixels.

Seeds the first row exactly, then advances by threshold compares only.

ns plane · 4 macros · legacy

The old framebuffer tier: span kernels that wrote into a real framebuffer. The shipped renderer has no framebuffer at all, so none of these is instantiated today.

draw_span / clear_planes
Kept as the byte-exact oracle mirror and the reference for the distance-light math the shipped tier reuses. Exercised only by unit tests.

06execution_model:

FlipJump has one instruction. a;b means: flip the bit at address a, then jump to address b. That is the entire machine. Everything above — arithmetic, tables, function calls — is built out of it by the standard library, which is why hex.* operations need hex.init to have run first: they are dispatching through truth tables that startup constructed.

This build uses a 32-bit word (w=32). dw is one hex-digit cell, so reg + 4*dw addresses the high four nibbles of a 16.16 register — its map-unit part. Because every runtime coordinate here has zero low bits, that slicing is exact rather than an approximation.

07how_to_poke_at_it:

Built programs are cached in scratchpad/fjmcache/ as b_<hash>.fjm. The generated .fj source is not normally kept — regenerate it with the config in scratchpad/cr/emit_hash.py, which is also how you check that a refactor left the emitted text byte-identical.

Find one seg’s code

Every seg’s constant blocks are labelled by index: seg<i>G_xorby for its pass-1 geometry and seg<i>R_xorby for its pass-2 render constants. Grep the label to read the baked values, then grep the call site to see which subsectors visit it. Three more suffixes appear in the walk: T (a two-sided boundary's attribution constants), F (its step-face constants) and S (a thing's sprite constants, tagged by subsector and thing rather than by seg index).
