

########## FEASIBLE-WITH-CAVEATS ##########

--- SUMMARY ---
Yes — one dereference can fetch 12 or 16 bits, and the `8` in `wflip hex.pointers.to_flip, dbit+8` is NOT a fetch width. It is an offset in the *value's own* bit numbering: `dbit = w + #w` (runlib.fj:3), a data slot is emitted as `;V*dw` (hex/memory.fj:8) so the stored word is V<<#w in the opcode's second word, and flipping bit `dbit+8` therefore adds 2^(#w+8) = 256*dw to it — i.e. logically `V += 256`, which is exactly the address of `read_ptr_byte_table` (`pad 256`, basic_pointers.fj:19-23). FlipJump has no fetch width at all: the dereference is a *jump* to the data opcode, whose jump-word IS the value, and the only thing that limits recoverable bits is that every distinct value must land on a distinct decoder opcode. So k bits per dereference costs a 2^k-opcode table based at exactly 2^k*dw, and nothing else in the mechanism (`read_ptr_and_flip_back`, `cleanup`, `to_flip`/`to_jump`/`ret_after_read_byte`) is width-dependent — the two `wflip to_flip, dbit+8` sites (xor_from_pointer.fj:36 and :52) just have to agree. dw-alignment of the pointer still suffices for any k < w - #w = 26 at w=32, so k=12 and k=16 need no new alignment. A 4-nibble single-dereference read prices at w(0.75@+5) + 11@+13 = 39@+173 against 84@+374 for today's `hex.read_byte 2`, a 2.15-2.16x win that is essentially independent of @, and the decode walk actually gets one op *cheaper* because popcount(16-bit value) = popcount(lo byte) + popcount(hi byte) and you pay one terminal return instead of two.

--- MECHANISM ---
HOW THE 8 ACTUALLY WORKS (traced, w=32 => dw=64, #w=6, dbit=38):

1. `set_flip_and_jump_pointers ptr` (basic_pointers.fj:73-77) writes the pointer value P into the *flip word* of the `to_flip` opcode and into the *jump word* of the `to_jump` opcode.
2. `wflip hex.pointers.to_flip, dbit+8` (xor_from_pointer.fj:36) does NOT touch the pointed-to memory. It XORs the constant 46 into the word holding P, turning it into P+46 (XOR == add because P is dw-aligned, so P's low #w=6 bits are zero, and 46 = 0b101110 has all its set bits below bit 6).
3. Executing `to_flip` flips the single bit at P+dbit+8. Offset dbit+8 = 46 lies at 46-w = 14 in the opcode's SECOND word, so the flip is worth 2^14 = 16384 = 256*dw.
4. A data slot is `;V * dw` (hex/memory.fj:8; doom's own emitter does the same at mapcompiler.py:398 `f"    ;{hex(...)} * dw"`). Its jump word is V<<6. Adding 256*dw makes it (V+256)*dw.
5. `to_jump` jumps to P; the slot executes `flip(0); jump((V+256)*dw)`; `read_ptr_byte_table` sits at exactly 256*dw (`pad 256`, basic_pointers.fj:19, and the "must be placed just after the startup" note at :5-6 is what forces the FIRST multiple). So control lands on table entry V.
6. Entry d (basic_pointers.fj:23-27) flips the top set bit of d into `read_byte` and jumps to entry d^topbit; the entry where d == its own top bit jumps to `ret_after_read_byte`. Cost = popcount(d)+1 ops.
7. `ret_after_read_byte` -> `to_flip` (re-armed at :47) flips bit dbit+8 back, restoring the slot; `cleanup` (:49-53) undoes the three redirections, including the SAME `wflip to_flip, dbit+8` at :52.

So the "+8" is log2(table base index). Nothing in steps 1,2,3,5,7 knows how many bits the value has.

WHAT A 12- OR 16-BIT PRIMITIVE WOULD BE:
* Slot: `;V * dw` with 0 <= V < 2^k, one dw opcode per k-bit value, flip word 0 (unchanged convention).
* `wflip to_flip, dbit+k` at both the setup and cleanup sites. dbit+12 = 50 -> bit 18 of the word -> 2^18 = 4096*dw. dbit+16 = 54 -> bit 22 -> 2^22 = 65536*dw. Both check out exactly.
* A 2^k-entry table at exactly 2^k*dw, i.e. `pad 4096` / `pad 65536` placed while the current address is still below that, generated by the identical formula generalised to a k/4-hex register: flip `read_word + ((#d-1)>>2)*dw + dbit + ((#d-1)&3)`, jump `table + (d^topbit)*dw`.
* A wider shared destination register (`read_word: hex.vec 4`) plus `hex.zero 4` / `hex.xor n, dst, read_word`.

ONE TABLE SERVES ALL WIDTHS. Entry d of the 2^16 table walks strictly downward (d^topbit < d), so entries 0..255 of the big table decode a byte correctly. If every slot is a 16-bit slot, `read_word` covers 1-, 2-, 3- and 4-nibble reads at one dereference each — the high hexes stay zero for narrow values, so `hex.xor n, dst, read_word` with n<4 is still correct.

ALIGNMENT: unchanged. P^(dbit+k) == P+dbit+k requires (P & (dbit+k)) == 0. dw-alignment zeroes P's low #w bits, and dbit+k = 38+k < 64 for all k <= 25. So dw-alignment covers k=12 and k=16 with room to spare. The hard ceiling is k < w - #w = 26 at w=32 (at k=26 the constant reaches bit 6 and you would need 2dw-alignment) — and 2^26 table opcodes makes that academic.

COST, in @ units (@ = log2 of total fj ops, README.md:75):
  today, `hex.read_byte 2, dst, ptr` (read_pointers.fj:63-66) = 2 x (w(0.75@+5) + 18@+27) = 84@ + 374
  proposed 4-nibble single deref = 4@ (zero dst) + w(0.75@+5) [24@+160] + [3@+13 machinery + 4@ zero read_word] + 4@ (xor 4) = 39@ + 173
  ratio 84/39 = 2.15 as @->inf, 374/173 = 2.16 as @->0, so ~2.16x at any @.
The decoder walk (omitted from the STL docstrings; see basic_pointers.fj:20-21 "Time Complexity: 4/8") is popcount(V)+1 for one 16-bit read versus popcount(lo)+1 + popcount(hi)+1 for two byte reads — 1 op cheaper, so there is no hidden linear penalty.

The write side generalises linearly too: `xor_byte_to_flip_ptr` is `rep(2, i) .xor_hex_to_flip_ptr hex+i*dw, 4*i` (xor_to_pointer.fj:106-108); a 4-nibble form is `rep(4, i) ... 4*i`, whose largest bit_shift is 12, flipping dbit+12..dbit+15 = 50..53 < 64, still inside the opcode.

SPACE: k=12 -> 4,096 opcodes (8,192 words); k=16 -> 65,536 opcodes (131,072 words), ~+0.26% of a ~50M-word image. The `pad` itself is close to free: padding op slots are pushed onto `padding_ops_indices` (assembler.py:225-228) and popped first by `get_wflip_spot` (assembler.py:148-150), and doom generates 16.1M wflip-chain links (assembler.py:84), so the ~65K pad slots are consumed immediately as real wflip ops.

CAN IT AVOID FORKING THE STL? I believe yes. `to_flip`, `to_jump` and `ret_after_read_byte` are exported globals of `ptr_init` (basic_pointers.fj:22-23), so doom can emit its own `pad 65536` + table + `read_word` + a copy of `read_byte_from_inners_ptrs` with `dbit+16`, entirely in its own namespace, without touching the vendored flipjump-151 STL. New macro names are additions, not renames, so the frozen-ABI rule is satisfied.

--- ESTIMATED_SAVING ---
Per 16-bit read, replacing `hex.read_byte 2, dst, ptr`: 84@+374 -> 39@+173. Delta = 45@ + 201, i.e. a factor of (84@+374)/(39@+173) = 2.16x at @=25 (2474 -> 1148) and 2.16x at @=12.5 (1424 -> 660) — the ratio is flat in @ because both sides are dominated by the same w(0.75@+5) term. Saving = 53.6% of the read. Against two plain `read_byte` calls with no pointer stepping (2 x (33@+173) = 66@+346) the win is smaller, ~1.74x at @=25, because the ptr_inc/ptr_sub overhead is what the n-form adds. For 3 nibbles (doom's PID_NIBBLES=3 in PID_BYTES=2 storage, config.py:98-104) the proposed form is 37@+173 (or 39@+173 if it shares the 4-hex register), also ~2.2x. Write side: `hex.write_byte 2` = 2 x (50@+211) = 100@+422 -> ~55@+221, ~1.9x. ⚠ ALL OF THIS IS UNVERIFIED ARITHMETIC ON THE STL DOCSTRINGS, NOT A MEASUREMENT — doom's own delta-measured note (src/fj/fixed_point.fj:182-183) says ~600 ops/byte where the docstring formula at @=25 predicts ~1,220, so the docstrings' @ coefficient is an upper bound (wflip cost is popcount of the address, ~@/2 on average). The per-read RATIO survives that correction; the whole-frame saving does not follow without running the bench, and I was asked not to write code. There are 106 `read_byte`/`read_byte_and_inc` call sites in src/fj (frame_render.fj alone has 62, seven of them the 2-byte n-form at :1160, :1454, :1462, :1478, :1486, :1567, :1591), plus the LUT row walkers, so the population is large — but per-frame dynamic counts are what matter and I have not measured them.

--- RISKS ---
ADDRESS-LAYOUT COLLISION WITH M13-HOTDATA. wall_renderer.py:1756-1770 already moved the hot pointer-walked arrays (`pclm`, `sfflag`, `sprflag`, packed LUTs, cm/byte EMIT tables) to just after startup precisely because wflip cost scales with the address's set bits (measured 78.54M -> 76.39M ops/frame). A 2^16 table must occupy opcodes [65536, 131072), so either it goes before the hot data (pushing hot data above 2^17 and perturbing that win) or after it (and then the hot block must end below op 65536). I did not measure the hot block's size. A 2^12 table is worse here, not better: it must sit below op 4096, which is BELOW `stl.startup_and_init_all`'s ~7,000 ops, so it would force splitting that macro into `stl.startup_and_init_pointers` + `hex.init` + `stl.stack_init`.
OP COUNTS WILL MOVE EVERYWHERE EVEN IF PIXELS DO NOT. Inserting 65,536 opcodes near address 0 shifts every later label, changing the popcount of a large fraction of the program's wflip targets. Per CLAUDE.md rule 2 an op-count change with byte-exact pixels means structure changed and must be investigated — here the cause is known and benign, but the gate output will not be a clean 'identical to the digit' and that must be stated up front rather than discovered.
A WIDENED ARRAY IS NOT READABLE BY THE OLD PRIMITIVE, AND FAILS SILENTLY-ISH. If a slot holds V >= 2^8 and something still reads it with `dbit+8`, bit 8 is already set so the XOR CLEARS it and the jump goes to (V-256)*dw — a wild jump into arbitrary code, not a wrong value. Any array converted to 16-bit slots must have EVERY reader and writer converted in the same commit (CLAUDE.md rule 5, fan-out: src/, scratchpad/ AND tests/). 106 read sites exist in src/fj alone.
INDEX ARITHMETIC IS BAKED IN MANY PLACES. Halving the slot count changes every `ptr_inc`/`ptr_sub` count, every `hex.mul_const w/4, ptr, ptr, nb*dw` (fixed_point.fj:190, 213, 240), `read_table_packed`'s `nb`, and the `SLOT_SHIFT` power-of-16 stride constraint documented at config.py:106-114. Those are exactly the 'a definition drifting from its call sites' hazard rule 5 warns about.
THE STL DOCSTRINGS I PRICED FROM DO NOT ACCOUNT FOR THE DECODER WALK. `read_byte_from_inners_ptrs` is documented `5@+13` (xor_from_pointer.fj:27) but my op-by-op trace only reconstructs those constants if the popcount(V)+1 table walk is excluded — the walk is priced separately as `4/8` at basic_pointers.fj:20-21. My conclusion that the walk gets CHEAPER when widened is sound (popcount is additive over bytes, and you pay one terminal return instead of two), but the absolute constants are less trustworthy than they look.
SHARED-REGISTER BLAST RADIUS. `hex.pointers.read_byte` is a global used by `write_hex`/`write_byte`/`zero_ptr` (write_pointers.fj:13-33), all of which call `read_byte_from_inners_ptrs`. Widening it in place changes those; adding a sibling `read_word` avoids that but means two decoder tables both demanding exact 2^k*dw bases. The safest shape (one 2^16 table, one 4-hex register, byte reads flipping dbit+16) makes the STL's own 256-entry table dead weight in doom's image.
M1 RESTORE-SET DEBT. `read_word` is a new global that the self-reset must either restore or be proven dead across the frame boundary (MEMORY.md: 'a feature isn't done until the M1 restore set carries its labels'; CLAUDE.md notes a hole in the restore set HANGS). The table itself is read-only `stl.fj` ops and is safe, but the register is not automatically covered.
R9 / VERIFICATION DEBT. A new dereference primitive is exactly the kind of thing the repo's history says four 'obviously equivalent' claims got wrong. It needs `deg_gate` plus, ideally, a negative control that mutates a table entry and requires the check to reject it — none of which I ran, since I was asked not to write code.

########## FEASIBLE-WITH-CAVEATS ##########

--- SUMMARY ---
Yes — the setup is amortisable, and the reason is stronger than expected: nothing in the fetch destroys it. `set_flip_and_jump_pointers` leaves four pieces of state (to_flip's flip-word = ptr, to_flip_var = ptr, to_jump's jump-word = ptr, to_jump_var = ptr), and `read_byte_from_inners_ptrs` restores every one of them before returning (xor_from_pointer.fj:51-53 exactly undo lines 36, 39, 47; to_jump and both shadows are never written at all). The write inner (`xor_hex_to_flip_ptr`) likewise restores to_flip's flip-word at xor_to_pointer.fj:141 and its jump-word at :146. So `read_byte n` = rep(n) of read_byte_and_inc pays w(0.75@+5) = 24@+160 per byte to rebuild state that was already correct. The cheap advance exists but is NOT a general "+dw": since to_flip/to_jump hold raw address words, `wflip to_flip, delta` costs popcount(delta) ops (~1-2), and base+i*dw == base XOR i*dw only when the base is 2^ceil(log2 n)*dw-aligned. That makes the amortised walk exact and ~2 ops/word for straight-line, compile-time-offset, pow2-aligned runs — which is precisely `read_table_packed nb`, `read_byte n`, `read_hex n`, `write_byte n`. It does NOT generalise cheaply to a runtime loop with a data-dependent stride, because there the carry is not compile-time known and re-deriving the delta costs about as much as the setup it replaces.

--- MECHANISM ---
STATE THE SETUP LEAVES (basic_pointers.fj:75-79 + logics.fj:88-93,149-156): `address_and_variable_xor n, address, var, src` xors src's nibbles into BOTH a raw memory word's bits (address+4i+j, as direct bit flips) and a hex shadow `var`. So set_flip_and_jump_pointers does three passes: clear to_flip by xoring with to_flip_var (w/4*(@+4)), clear to_jump+w by xoring with to_jump_var (w/4*(@+4)), then one quadrupled pass xoring ptr into all four (w/4*(@+12)) = w(0.75@+5) total. Post-condition: word@to_flip == to_flip_var == word@(to_jump+w) == to_jump_var == ptr; to_flip+w == 0; to_jump's flip-word == 0.

DOES THE FETCH DESTROY IT? No — it is exactly symmetric (xor_from_pointer.fj):
  :36  wflip to_flip, dbit+8            -> undone by :52  wflip to_flip, dbit+8
  :39  wflip to_flip+w, read_ptr_and_flip_back  -> undone by :46 (->cleanup) then :53 wflip to_flip+w, cleanup
  :47  wflip ret_after_read_byte+w, to_flip     -> undone by :51 wflip ret_after_read_byte+w, to_flip
to_flip_var, to_jump_var and to_jump are never written. (The ^(dbit+8) is an exact +46 because ptr is dw-aligned and dbit+8 = 46 < dw = 64 at w=32; it adds 256 to the cell's stored value, and the read table sits at op-index 256 (basic_pointers.fj:19-27), so "+256" IS the table base — that is the whole dereference.) The write inner is symmetric too: xor_to_pointer.fj:123,126,129,132 walk to_flip's word through dbit+{0,1,3,2}+shift and :141 restores it to ptr; :146 restores the jump-word.

THE CHEAP ADVANCE: to_flip's flip-word and to_jump's jump-word are raw address words, so `wflip to_flip, K` costs popcount(K) ops for a compile-time K (README: wflip's cost is its on-bit count; corroborated by stl.fcall being "@-1" for two label-sized wflips, ptrlib.fj:88-93). Walking slot i -> i+1 needs K = (i^(i+1))*dw on BOTH words: ~2 ops each, ~4 ops/step, averaged. This is exactly the trick the stl already uses at xor_to_pointer.fj:136-143, where `to_flip+dbit+0;prepare_flip_bit1` flips one bit (#w) to advance a jump target from after_flip_bit0 to after_flip_bit1 inside a `pad 4` block — a 1-op address advance. And ptr_wflip (xor_to_pointer.fj:154-170) already increments to_flip's raw word by direct `bit.exact_not to_flip+i` flips rather than re-deriving from ptr, with compile-time-known carries because the base is w-aligned. So the precedent for both halves (mutate the raw word; advance by constant XOR) is in the library.

THE PRECONDITION: base + i*dw == base XOR (i*dw) only if base's bits [#w, #w+ceil(log2 n)) are zero, i.e. base is 2^ceil(log2 n)*dw-aligned. For `read_table_packed nb` the base is table + idx*nb*dw, so a `pad nb`-aligned table with pow2 nb (nb=4 viewangletox, nb=8 lnbox) satisfies it for FREE. Non-pow2 nb (3 for yslope/slopediv_recip, 5 for the thing row, 13) needs the stride padded up to the next power of two (+33%/+60% on that table's data ops) — or no amortisation.

SHAPE OF THE AMORTISED BLOCK (needs NO stl change; to_flip/to_jump/read_byte/ret_after_read_byte are exported globals and read_byte_from_inners_ptrs is a public macro, so this can live in src/fj/fixed_point.fj next to read_table_packed):
  set_flip_and_jump_pointers ptr                    // once: w(0.75@+5)
  rep(nb, k) {
     read_byte_from_inners_ptrs                     // 5@+13
     hex.zero 2, dst+2k*dw ; hex.xor 2, dst+2k*dw, read_byte
     wflip to_flip, (k^(k+1))*dw                    // ~2 ops
     wflip to_jump+w, (k^(k+1))*dw                  // ~2 ops
  }
  wflip to_flip, (nb-1)*dw ; wflip to_jump+w, (nb-1)*dw   // restore the shadow invariant
Per-byte ptr_inc (9@+14) disappears entirely; if the caller needs ptr advanced, one `ptr_add ptr, nb` (13@+26) replaces n incs.

WRITE SIDE: identical, and it applies to both variants. `write_byte` (write_pointers.fj:30-35) = setup + fetch + xor + xor_byte_to_flip_ptr, and both inner macros restore to_flip, so `write_byte n` (write_pointers.fj:77-80) is amortisable the same way (both words must advance, since write_byte read-modify-writes). `xor_byte_to_ptr n` (xor_to_pointer.fj:63-66) is the cheaper case: it only calls set_flip_pointer (w(0.5@+2) = 16@+64) and only to_flip needs advancing, so ~2 ops/step.

WHERE IT DOES NOT WORK: a runtime loop stepping a runtime pointer (e.g. stream_render.fj:110-127 emit_prefix's `ploop`, sim's band walks). There the offset is not compile-time, carries are data-dependent, and forming the xor-delta costs ptr_inc (9@+14) + delta formation (w/4*(@+4) = 8@+32) + applying it to all four targets (w/4*(@+12) = 8@+96) ~= 25@+142, i.e. the same as the 24@+160 setup it replaces. A carry-aware variant (touch only nibble 1, branch on the 1-in-4 carry) plausibly lands at 3-5@ expected, but I have NOT worked that design out and will not claim it.

--- RISKS ---
STALE-SHADOW FOOTGUN, and it fails silently and catastrophically. During the walk, word@to_flip != to_flip_var. Any nested pointer macro inside the block calls set_flip_pointer, whose first pass is `address_and_variable_xor w/4, to_flip, to_flip_var, to_flip_var` (basic_pointers.fj:65) — with a stale shadow that leaves the raw word at X^Y instead of 0, and the next dereference jumps to a garbage address. `stl.call`/`stl.return` count (ptrlib.fj:69). Mitigation: keep the block straight-line and restore the net offset with two constant wflips at the end; audit every call site for nested pointer ops / stack calls.
ALIGNMENT IS AN INVISIBLE PRECONDITION AND ITS VIOLATION IS NOT A CRASH. If base+i*dw carries (base not 2^ceil(log2 n)*dw-aligned), the XOR walk reads a DIFFERENT cell — wrong data, right shape, wrong pixels. It must be an emit-time assert on the table label's alignment and stride, not a comment.
NON-POW2 STRIDES NEED PADDING. nb=3 (yslope, slopediv_recip), nb=5 (thing row), 13 (line row) must be padded to 4/8/16 to get a carry-free run: +33%/+60%/+23% data ops on those tables, against an assembler that CLAUDE.md documents as MEMORY-bound. The code-size side goes the other way (each removed setup expansion is w(0.75@+29) = 24@+928 of emitted ops), so the net space effect has to be measured per table, not assumed.
HIGHEST BLAST RADIUS IN THE PROGRAM. Every LUT read, every collision row, every band walk goes through this machinery. Any error is a global miscompare, so this needs deg_gate (4 viewpoints byte-exact AND op counts to the digit) plus m5_gate, not a spot check — and per CLAUDE.md rule 2 the oracle does not move, so a byte diff is a hard stop.
OP COUNTS MOVE EVERYWHERE. The gate asserts op counts to the digit, so every recorded number in docs/tests/handoffs becomes stale in the same commit. That is expected here but it removes the 'op count unchanged' safety signal for anything else riding in the change.
MY COST MODEL FOR THE ADVANCE IS INFERRED, NOT MEASURED. I claim `wflip a, K` costs popcount(K) ops from the stl README plus stl.fcall's documented '@-1' for two label-sized wflips. If the assembler emits wflip differently (a shared wflip block with fixed overhead), the ~4 ops/step becomes larger — though it would have to become ~200x larger to erase the win.
BENEFIT IS CONCENTRATED IN FIXED-SIZE BLOCK READS. Runtime loops with a data-dependent stride (stream_render.fj:110-127 and the band walks) get nothing from the constant-XOR form; if those dominate the frame rather than read_table_packed, the frame-level win is much smaller than the per-call ratios suggest.
INTERACTS WITH QUESTION A. If a single dereference can be widened to fetch 4 nibbles, it shrinks the per-fetch term that amortisation is dividing into, so the two wins multiply sub-additively. Pricing them independently and adding will overstate the total.

--- RISKS ---
NAMING IS THE REAL RISK. There is no third size-noun in the stl and 'word' already means w bits (runlib.fj:2). read_word ships a macro whose name contradicts the language's own vocabulary; a plural like read_nibbles has only fill_bytes/copy_bytes as precedent, and those take a RUNTIME count while a wide read would take a compile-time n. Get the name settled before writing the doc block.
The 8-bit ceiling is a TABLE, not a constant. read_ptr_byte_table is 'pad 256' + rep(256, d) of stl.fj ops (basic_pointers.fj:19-27), with a header note that it must sit just after the startup. Widening the read to 12 or 16 bits means a 4096- or 65536-entry table in EVERY program that calls ptr_init, plus a wider hex.pointers.read_byte than the 'hex.vec 2' at :29-30. That is a global space cost paid by programs that never call the new macro — an stl-wide regression the doc-block Space Complexity must state honestly.
Widening hex.pointers.read_byte or the table changes ptr_init's exports and layout, which is exactly what CONTRIBUTING forbids ('Don't change the stl-api, only offer new options'). A separately-initialised table keeps ptr_init untouched but then needs its own <name>_init, its own @requires line, and a place in startup_and_init_all.
Complexity comments are unchecked by CI (no validator found anywhere in flipjump/ or tests/). A wrong Time Complexity ships silently and is then quoted by every downstream reader — the exact failure doom's Performance-Claims rule exists to prevent.
Committing to 1.5.1 alone does not reach doom: the editable install resolves to the checked-out branch, which is perf-asm-10min and is NOT a descendant of 1.5.1 ('git merge-base --is-ancestor 1.5.1 perf-asm-10min' → NO). A macro added on 1.5.1 will look absent to every doom build until the branches are reconciled.
953ddd9, the template to copy, left flipjump/stl/hex/README.md:30 and programs/hexlib_tests/basics2/README.md stale. Following it without adding the doc rows repeats a known miss a maintainer review will catch.
The stl-prefix parse cache (flipjump/assembler/fj_parser.py, pinned by tests/unit/test_parse_cache.py) is keyed on stl file mtime/size, so editing an stl file invalidates it correctly — but every doom build after the edit re-parses the whole stl prefix once, and any stale .fjm under tests/compiled/ must be rebuilt rather than trusted.

--- SUMMARY ---
There are 225 pointer call sites in `src/fj/*.fj`, but only about 150 are LIVE in the shipped `game` tier — `plane_bands.fj` (12), `plane_render.fj` (7), `m1_reset.fj` (6, comments only) and ~32 of `stream_render.fj`'s 40 are dead code, because `ascode=1`/`stack=1`/`w2s=wpx=0` rep-gate `half_walk`, `band_walk`, `emit_prefix/suffix`, `flush_frame` and the WPX/W2S wall emitters to zero, and `plane.build_bands`/`plane.draw_span*` are never emitted at all. Of the ~6,700 dereferences per frame I can account for, roughly 78% are SINGLE-byte random-index reads of the per-column arrays (`drawn[x]`, `pclm[x]`, `sfflag[x]`, `sprflag[x]`) which a wider primitive cannot help — the biggest single population is pass-1's occlusion prescan at 840 `read_byte`s/frame. The multi-byte runs worth attacking are ~1,500 removable dereferences with a 2-byte primitive (~2,400 with a 4-byte one), and each removed dereference is worth `set_flip_and_jump_pointers` + the `ptr_inc` it carries = 33@ + 174. That lands at roughly 1.1M-1.6M ops/frame (2-byte) or 1.9M-2.6M (4-byte) against a ~29.4M shipped spawn frame, i.e. 3.6%-8.7% — and the repo's own realisation factor would discount that to 1.6%-3.9%. The hard blocker is that 8 bits is architectural, not a macro choice: `read_byte_from_inners_ptrs` decodes through a 256-entry table pinned at op 256, so 16 bits needs a 65,536-entry table and 32 bits is impossible; the cheaper alternative (re-arm once, step the armed pointer) is documented in this repo as a dead end, though I believe that verdict does not cover the ALIGNED-pair case.

--- MECHANISM ---
HOW A READ COSTS WHAT IT COSTS (w=32, from the docstrings; the arithmetic is mine).
  D = set_flip_and_jump_pointers = w(0.75@+5) = 24@ + 160  -- paid PER DEREFERENCE
  read_byte      = D + 9@+13  = 33@ + 173
  read_byte_and_inc = D + 18@+27 = 42@ + 187   (of which ptr_inc = 9@+14)
  write_byte     = 41@ + 197 ;  write_byte_and_inc = 50@ + 211
  ptr_index      = w(2.25@+5.25) + 0.25@ = 72.25@ + 168   -- NOT a dereference; pure hex arithmetic, so it is NOT in the measured set_flip_and_jump_pointers total and a wider read does not touch it
  read_byte n / read_hex n = n x (the _and_inc form) + ptr_sub
  hex.read_table_packed nb (src/fj/fixed_point.fj:186-191) = `rep(nb, k) .read_byte_and_inc` -- nb FULL dereferences

SAVING PER ELIMINATED DEREFERENCE, two models that agree:
  (a) conservative -- only D and the ptr_inc are shared: (24@+160) + (9@+14) = 33@ + 174
  (b) the prompt's model -- the decode widens too: amortised_n_bytes = (29+4n)@ + 173
      (checks out: n=1 -> 33@+173 = read_byte exactly; n=2 -> 37@+173 = the prompt's 4-nibble figure)
      n read_byte_and_inc - [amortised + one ptr_add] = (38n-42)@ + (187n-199)
      n=2 -> 34@+175 ; n=4 -> 110@+549 (vs (a)'s 3x(33@+174) = 99@+522)
  The two are within 10%, so I use (33@ + 174) per removed dereference throughout.

MODEL VALIDATION against a real measurement: `src/fj/m1_reset.fj:22-24` records `hex.read_byte` at 628 ops replaced by a constant-address `m1.readbyte` at 111.4 -- a 516.6-op saving for eliminating exactly one D. D = 24@+160 at that small program's @ (~13.8) = 491. Model 491 vs measured 517, +5%.

WHY 8 BITS IS ARCHITECTURAL, NOT A MACRO CHOICE. `read_byte_from_inners_ptrs` (xor_from_pointer.fj:29-54) works by `wflip to_flip, dbit+8` -- flipping bit 8 of the TARGET WORD's jump address so it becomes (256+v)*dw, which IS `read_ptr_byte_table + v` because the table is pinned at op 256 (`basic_pointers.fj:19-27`, `pad 256` + `rep(256, d)`). A 16-bit read needs `wflip to_flip, dbit+16`, a 65,536-entry table pinned at op 65,536 (~65k words -- cheap against a 68.2M-word image) and a hex[:4] `read_byte` global; the chain length per read grows from popcount(8 bits) to popcount(16 bits). A 32-bit read needs 2^32 entries and is IMPOSSIBLE. So TWO BYTES is the practical ceiling for a genuinely wider decode.

THE CHEAPER ROUTE, AND THE REPO'S OBJECTION TO IT. Keep the 256-entry table; arm the pointer ONCE and do two 8-bit walks off it. `docs/handoff-constaddr.md` §5 calls this "a genuine dead end": "stepping an armed pointer means xoring old ^ new into the address fields, and computing that delta costs ~900 ops -- more than the ~400-op re-arm it replaces." I believe that verdict is TRUE FOR A GENERAL STEP AND FALSE FOR AN ALIGNED PAIR, and the counter-example is already shipping in this repo. `frame.pixel_tramp` (frame_render.fj:118-128) does `pad 2  // align ret to 2*dw so the redirect-bit flip is carry-free` and then flips one bit at offset `w + (#dw - 1)`. The same holds here: to_flip holds ptr + dbit + 8 with dbit = w + log2(dw) = 38 and dbit+8 = 46 < dw = 64, so if ptr is 2*dw-ALIGNED then ptr -> ptr+dw flips exactly bit log2(dw) with no carry. Stepping the armed pointer across an aligned pair is then `wflip to_flip, dw` + `wflip to_jump+w, dw` -- TWO ops, not ~900. Cost of such a `read_byte_pair`: D + 2x(read tail 9@+13) + ~4 wflips ~= 42@ + 190, against 2 x read_byte_and_inc = 84@ + 374. Saving ~42@ + 184, consistent with the 33@+174 figure above.
  UNVERIFIED. I have not built or measured this. The repo has been burned four times by "obviously equivalent" claims (CLAUDE.md rule 3), and the alignment precondition is exactly the kind of thing that silently fails.

WHAT ELSE MUST CHANGE. A 16-bit read requires the two bytes to live in ONE WORD. The packed-byte LUT idiom is one byte per word (`;value*dw`, `generate_packed_lut_fj`), so a real 16-bit read of `throw`/`lnbox`/`lnrow`/`sprbank`/`bklin` means re-baking them as `;(v0 | v1<<8)*dw` -- an emitter-side change, and every consumer's nibble offsets move. The armed-pair route needs no relayout, only 2*dw alignment, which the power-of-two strides (SPR_SLOT_STRIDE=16, SPR_BLOCK_STRIDE=64, SLOT_SHIFT a power of 16) already give for even byte offsets. For RUNTIME-WRITTEN arrays (`spslot`, `sfslot`, `pclm`) the writer and reader must change in the same commit, and `hex.pointers.read_byte` is a SHARED global -- the R42 hazard (`handoff-constaddr.md` §6) applies to any new handler.

WHAT THIS CANNOT REACH. `ptr_index` is quoted at 32% of all pointer spend (44 sites x 1554.2 ops, handoff-constaddr.md §6) and a wider read does not touch it. Nor does it touch the ~5,200 single-byte per-column dereferences, which are the actual bulk. Those need the constant-address dispatch (C1), which `handoff-constaddr.md` §9 documents as ATTEMPTED AND BLOCKED (two wflip-based return mechanisms in flight at once -- the R42 hazard).

--- STRONGEST_OBJECTION ---
The claim's own SHAPE pseudocode is wrong, and wrong in the one place that is globally destructive. The advance deltas telescope: XOR over k=0..nb-1 of (k^(k+1))*dw = (0^1)^(1^2)^...^((nb-1)^nb) = 0^nb = nb*dw. So after the loop to_flip and to_jump+w hold base XOR (nb*dw), not base + (nb-1)*dw. The sketch's restore line then XORs (nb-1)*dw, leaving base XOR ((nb^(nb-1))*dw) = base XOR ((2nb-1)*dw) -- for nb=4, base XOR 7*dw, i.e. off by 7 slots. That permanently breaks the invariant word@to_flip == to_flip_var, and the break is INERT until the next set_flip_pointer / set_flip_and_jump_pointers anywhere in the program (basic_pointers.fj:65-66 clears the raw word by xoring the shadow into it, which only works if they match). The failure mode is therefore not a crash at the fault site but a wrong dereference address -- a wild jump -- arbitrarily far away. Two subsidiary points make this worse rather than better: (a) the final advance is also the ONE step whose XOR is not an add, because base is a multiple of nb*dw but not of 2*nb*dw, so bit #w+log2(nb) may already be set -- it happens to be harmless only because that value is never dereferenced and XOR is self-inverse, which means the correct fix is `wflip to_flip, nb*dw` (or drop the last advance and keep (nb-1)*dw), not the line as written; (b) there is no compile-time guard anywhere in the stl for this invariant, and the block is a global critical section in which any future inserted call that touches hex pointers -- notably stl.call/stl.return via ptrlib.fj:69 `hex.ptr_jump hex.pointers.sp`, or any hex.mul/hex.div that routes through them -- silently consumes a stale shadow. In a repo whose top rule is byte-exactness, the amortised block is a hand-maintained invariant with no netting, and the claim's own worked example already gets it wrong.

--- STRONGEST_OBJECTION ---
The one true feasibility constraint the claim never states: the table must land on the FIRST multiple of 2^k ops, and `pad` does not enforce that — `align_current_address` (preprocessor.py:249) just rounds up to the next multiple, so if anything ever pushes the pre-table image past 2^16 ops the flip silently targets 2*2^16*dw and every dereference jumps into garbage, with no assembler diagnostic. Worse, the padding it creates is executable-hostile: `insert_padding` (assembler.py:225-228) emits `0;0` ops, and address 0 is `;code_start` (runlib.fj:23), so control falling into the ~58.5K padded ops re-enters startup. The pad+table must therefore live inside a jumped-over region, and every k you add hard-reserves the front of the image. Doom can satisfy this today (the `;__hot_end` jump in the entry part), but it makes the front-of-image layout a load-bearing, unasserted invariant — exactly the class of thing CLAUDE.md's "ORDER IS THE CONTRACT" warns about. Second strongest: the cited seven call sites are `rep(PID_BYTES-1, k)` with PID_BYTES==1 by default (config.py:86,105), so they emit nothing in the shipped tier — the claim's headline evidence for where the 2.15x lands is inert code.
